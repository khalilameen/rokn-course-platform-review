# Rokn mobile

Rokn is an Arabic-first learning app built around short vertical course reels.
The intended journey is simple: watch a short reel, apply it in a small project,
save useful reels for later, earn or buy Rokn coins, then unlock the next course.

## Run locally

```powershell
npm ci
npm start
npm run android
```

Start Metro first, then build and open the current checkout in the emulator. A
previously installed APK does not receive JavaScript from a stopped or unrelated
Metro server.

For a device-installable test build:

```powershell
npm run apk
```

The output is `artifacts/Rokn-test.apk`. It is debug-signed and includes the
local demo. Use `npm run apk:direct` only with the production API URL, Firebase
configuration, and release signing key in place.

## API configuration

The mobile app never contains provider secrets. Copy `.env.example` to `.env`
and set the deployed Rokn API before creating a production build:

```dotenv
EXPO_PUBLIC_API_URL=https://api.example.com/api/v1/
```

The URL must expose `GET /auth-methods` and the authenticated routes in
`rokn-backend/routes/api.php`. Do not ship a build pointed at a development URL
unless it returns those routes successfully.

## Login and notifications

- Login is social-only: Google, TikTok, and Facebook. OTP and phone/password
  are legacy routes and are intentionally not offered by the new mobile flow.
- The server controls which providers appear as available through
  `GET /auth-methods`; an unavailable provider is disabled instead of letting
  a student go through a failing provider screen.
- Android learning reminders work locally after opt-in. Production push
  campaigns additionally need the backend Firebase service account and a
  deployed queue/scheduler.

## Distribution channels

`npm run apk` creates a debug-signed test APK with the local demo enabled.
`npm run apk:direct` creates the production direct-distribution APK, while
`npm run aab:play` creates the consumption-only Google Play AAB. The app uses
`EXPO_PUBLIC_DISTRIBUTION_CHANNEL` at bundle time, so always rebuild after
changing channels or API configuration.

## iOS native dependencies

`ios/Podfile.lock` is generated by CocoaPods and must never be edited by hand.
After changing a native JavaScript dependency, regenerate and verify it on
macOS before creating an iOS release:

```bash
npm ci
cd ios && pod install && cd ..
npm run verify:ios-lock
```

The iOS CI job runs the same verifier, then uses `pod install --deployment` so
a stale, incomplete, or silently rewritten lock file cannot reach Xcode.

## Demo content

The no-account demo deliberately includes a complete thirty-step freelance
course, local coin tasks, saved reels, projects, and a course-opening flow. It
is for evaluating the journey only; real accounts read published courses and
wallet data from the API.

## Verification

Run the release gate before producing an artifact:

```powershell
npm run verify:release
npm run verify:ios-lock
```

This checks release configuration, TypeScript, ESLint, Jest contracts,
accessibility rules and production dependencies. Native Android and iOS builds
run in `../.github/workflows/mobile-ci.yml`; GitHub Actions are pinned to immutable
commits.

The protected Android staging suite is under `e2e/maestro`. It requires the
documented OAuth test account, staging courses and a signed staging APK. Missing
credentials fail the command instead of reporting an incomplete smoke test as
successful.
